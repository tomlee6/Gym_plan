# Rotate secrets

All secrets are in Secrets Manager in ap-southeast-2, named
`flexgym-<env>/<NAME>`. ECS reads them **when a task starts**, so after
changing a value, restart both services:

```sh
for s in api worker; do
  aws ecs update-service --region ap-southeast-2 --cluster flexgym-prod \
    --service flexgym-prod-$s --force-new-deployment
done
aws ecs wait services-stable --region ap-southeast-2 --cluster flexgym-prod \
  --services flexgym-prod-api flexgym-prod-worker
```

During the rolling restart, old and new tasks run side by side for a few
minutes with different values. Each section says what that means.

A good random value (64 characters, URL-safe):

```sh
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

| Secret | Origin | Who is affected by rotating |
|--------|--------|-----------------------------|
| `JWT_SECRET` | generated by CDK | every signed-in user's access token |
| `STORAGE_SIGNING_SECRET` | generated by CDK | outstanding signed storage URLs |
| `COGNITO_CLIENT_SECRET` (as `HUB_CLIENT_SECRET`) | generated by Cognito | sign-in |
| `database` | generated by RDS | the API and worker database connection |

## JWT_SECRET

Signs API access tokens. **Rotating it invalidates every access token, so
everyone is signed out of their access token at once.** Refresh tokens are
stored in the database, not signed with this secret, so they survive: the
apps get a 401, refresh, and carry on. Users only notice if their refresh
token has also expired.

While old and new tasks overlap, a token issued by one may be rejected by the
other; clients simply refresh again. Rotate at a quiet time.

```sh
aws secretsmanager put-secret-value --region ap-southeast-2 \
  --secret-id flexgym-prod/JWT_SECRET --secret-string "<new value>"
```

Then restart both services.

Rotate it immediately if it may have leaked: with it, anyone can mint access
tokens for any user.

## STORAGE_SIGNING_SECRET

Signs storage URLs the API issues. URLs signed with the old value stop
working, so an upload in progress from the phone may have to request fresh
URLs (the app retries part uploads). Presigned S3 URLs are signed by the task
role and are not affected.

```sh
aws secretsmanager put-secret-value --region ap-southeast-2 \
  --secret-id flexgym-prod/STORAGE_SIGNING_SECRET --secret-string "<new value>"
```

Restart both services.

## COGNITO_CLIENT_SECRET (Cognito app client)

Cognito generates it with the app client, and the Auth stack copies it into
`flexgym-prod/COGNITO_CLIENT_SECRET`; nothing is set by hand. A Cognito app
client cannot change its secret, so rotating means a new client: rename the
client in `infra/lib/auth-stack.ts` (CDK then replaces it), deploy, and
restart both services. Sign-ins started before the restart fail once and
work on retry.

## Database password

RDS generated it; the secret `flexgym-prod/database` holds `username` and
`password`. To rotate by hand:

```sh
NEW=$(node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))")
aws rds modify-db-instance --region ap-southeast-2 --db-instance-identifier flexgym-prod \
  --master-user-password "$NEW" --apply-immediately
aws secretsmanager get-secret-value --region ap-southeast-2 --secret-id flexgym-prod/database \
  --query SecretString --output text > /tmp/db.json   # edit "password", then:
aws secretsmanager put-secret-value --region ap-southeast-2 --secret-id flexgym-prod/database \
  --secret-string file:///tmp/db.json && rm /tmp/db.json
```

Restart both services straight away; running tasks keep their old connection
pool until a reconnect fails. Prefer a quiet time.

## After any rotation

- Check the dashboard (`flexgym-prod`) for 5xx and failed jobs for 15 minutes.
- Note the date and reason in the team's change log.
